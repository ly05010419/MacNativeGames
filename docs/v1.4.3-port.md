地区复测使用 `scripts/mac_v143_smoke.py`：`--profile` 指向独立的旧版存档基线，`--output` 每轮使用新目录，`--slot` 必须与现有桌面入口使用同一个游戏槽；不能另建槽绕过单实例保护。脚本默认测试实际打包 App，逐点复制并只修改两个已知位置向量，读档后热身 25 秒、固定镜头 30 秒、转三次镜头并切换三态画质。日志、原始帧数据（退出后 gzip）、截图和运行时哈希均保存。坐标只是候选，必须核对地面、室内外及遮挡；旧报告会被保留，不能用重复目录冒充复测。后续脚本还记录单调时钟窗口和实际游戏帧数/秒，便于与耗时均值交叉核对。

HUD 时钟复测使用 `scripts/verify_running_clock.py`，挂接已经持有同一游戏槽的精确测试进程，不负责启动/移动/保存/关闭；看到真实用户输入即停止。默认间隔 120 秒，最长 1200 秒，避免超过完整游戏日后出现两张 HUD 截图无法辨别的日数回绕。它只检查世界时钟，不代替移动、物理、动画或过场验证。

长局监测使用 `scripts/mac_v143_soak.py --pid <测试进程> --test-root <独立测试目录> --duration 14400`，先确认已进入可游玩场景、初始画质和补帧均关闭。目录必须有 `launch.json` 中标明 `TOTK_SLOT_OWNER=codex`、同目录 profile 和 input.txt；实际桌面启动的可写路径使用标准用户数据目录下的 `tests`，不能引用外部卷中的旧存档路径。长局禁用 `DM_NVN_TSV`，每分钟保存 RSS/CPU、最近游戏帧号、音频 RMS/峰值及累计 underrun/overrun；帧号来自每 300 帧的周期日志，短窗口帧率只能近似。每 10 分钟截图/短转镜头、每 15 分钟切画质、每小时切补帧；这些间隔可通过参数缩短作监测器实测。槽身份、进程或日志被替换、真实用户输入、90 秒没有周期帧推进时停止控制，保留现场。完成运行仍须人工检查截图、音频变化和日志，不能仅以脚本退出当成全游戏通过；完成后关闭自己的测试局，再严格复查 App 签名。

真实桌面测试的重开行为：普通 `open` 同一正在运行的 App 会由 LaunchServices 激活现有窗口，实测仍是原来的测试 PID，不会另外执行启动器或切换到正式 profile。game-slot 的用户抢占只在确实启动新用户进程时发生。真实输入会让监测器停止，但当前窗口仍属于独立存档；因此测试标题必须清楚标注副本；未发生用户接管时，应正常关闭代理测试再交付。若真实用户已接管，立即停止控制并保留当前窗口，明确告知它仍为测试存档副本，不能擅自关闭或切换 profile。

Mac 内存补采：`xcrun clang -O2 -Wall -Wextra -Werror scripts/mac_process_memory.c -o /tmp/totk-memory`，随后 `/tmp/totk-memory <game_pid> <game_start>`。字段直接来自本机 SDK 的 `proc_pid_rusage(RUSAGE_INFO_V4)`，分别保留 `resident_size`、`phys_footprint` 和进程生存期的 `lifetime_max_phys_footprint`，不将 RSS 当成其他内存指标的替代。第二参数使用同一游戏槽的启动秒数，PID 重用/不匹配时拒绝采样；真实正向和错误启动时间负对照通过。本轮约 44 分钟后开始每分钟补采到 `process-memory.jsonl`，不能冒充从零时刻采集的完整曲线；首次 footprint 约 5.15 GiB、当时全程峰值约 5.21 GiB，RSS 约 1.70 GiB。进程全程峰值仍覆盖更早的时间。

渲染器日志 `内存…常驻…MB` 的历史标签实际由 `hle_nvn.c` 的 `TASK_VM_INFO.phys_footprint` 提供，不是 `ps` RSS；本轮独立采样按真实字段名记录，避免混用。

补帧重建/帧资源复测（在 `games/totk` 下编译）：

```sh
xcrun clang -fobjc-arc -O2 -Wall -Wextra -Werror \
  -Iruntime -Ithird_party/d2r_gfx/gfx/nvn \
  scripts/mfx_resize_probe.m runtime/game_slot.c \
  -framework Foundation -framework Metal -framework MetalFX -framework QuartzCore \
  -o /tmp/totk-fi-resize
TOTK_GAME_SLOT_DIR="$HOME/Library/Application Support/MacNativeGames/TOTK/game-slot" \

```

该探针会取得同一个游戏槽；未设置 `MFX_RESIZE_ENCODE` 时只检查资源构建，设置时额外检查真实编码、完成回调持有和黑色读回。用同一命令额外设置 `TOTK_MFX_FI_CACHE=0` 作无缓存对照。结果是受控小场景，不代替正式 App 游玩。所有 GPU 实验均串行，用户进程优先。

只读汇总使用 `scripts/summarize_mac_soak.py <soak-report.json> --memory <process-memory.jsonl> --log <game.log> --instrumentation <vmmap-instrumentation-window.json>`，输出 JSON；每项输入记录本次实际解析字节的 SHA-256。它仅按监测首末帧范围统计相对长帧，画质/补帧请求前后一分钟排除于分组计数之外，分组速率仅为粗粒度游戏帧数/秒。模式标签需与运行时切换日志核对，不将不同天气、时间、镜头或缓存状态的分组用于因果性能比较。诊断时间窗口按相邻分钟采样及 300 帧粒度保守标注，不证明工具导致了其中每个尖峰。本轮帧 453049 的 1600.2 ms 位于 `vmmap` 对应范围；936.2 ms 和 704.9 ms 两个编译尖峰位于该范围之外，仍须记录为实际观察。

## 1.4.3 场景渲染分辨率（TOTK_RENDER_RES，外部贡献移植）

1.0.0/1.1.2 的 `TOTK_RENDER_RES=<w>x<h>` 已移植到 1.4.3：只改场景渲染尺寸，UI 与输出分辨率不变；未设置或为 `0` 时不打补丁，走游戏自身尺寸（手持 1280x720 / 座机 1600x900）。

1.4.3 的代码形状与 1.0.0 不同：两个维度都经 `s0` 转换，且 `w9` 在补丁点之后仍被 `main+0x585e64`（输出尺寸）使用，因此不能用 `x9` 做 adrp，改用本函数内纯临时的 `x3`。

| 地址 | 原指令 | 补丁后 |
| --- | --- | --- |
| `main+0x585e48` | `scvtf s0, w11` | `adrp x3, <数据页>` |
| `main+0x585e50` | `str s0, [x19, #0xcc4]` | `ldp s0, s1, [x3, #16]` |
| `main+0x585e54` | `scvtf s0, w10` | `str s0, [x19, #0xcc4]` |
| `main+0x585e60` | `str s0, [x19, #0xcc8]` | `str s1, [x19, #0xcc8]` |

所有选择渲染尺寸的分支都汇合于 `0x585e48`（`0x585f50` 的分支只重新装载 w11/w10 后跳回）。值写在与实时步长补丁共用的数据页 `+16`。四处原始指令在写入前逐一校验，不匹配即 `runtime_fail("render resolution patch: main does not match 1.4.3")`，不会半途破坏主模块。

验证：分支与寄存器活性分析（`x3` 在整个函数内未被读写，`x9` 活性确认）、原始指令逐一比对、Unicorn 仿真（补丁前 1600x900 / 输出 1920；补丁后 960x540 / 输出仍 1920），以及本机 1.4.3 实机 `probe` 运行（日志出现 `1.4.3 render resolution patch: scene render size 960x540`，模块自检 `{"status":"pass"}`）。示例：`TOTK_RENDER_RES=1280x720`。Mac 默认不设，画面和以前一样（项目规则：Mac 上不降分辨率，这个变量只给想自己调的人用）。

iPhone / iPad 和 IPA 导出（合并时补上，和 `game_patches.c` 的做法一样）：手机上不能改代码，补丁只能在 Mac 上导出时编进去。导出时设了 `TOTK_RENDER_RES` 才会编进去；手机运行时先核对编进去的指令，再把尺寸写到数据页：手机自己设的 `TOTK_RENDER_RES`，没设就用游戏的掌机尺寸 1280x720。导出时没编进补丁的，手机上照旧用游戏自己的尺寸，设了变量也不会去改代码。

1.2.1 不需要另做：它走 `game_patches.c`，`game_version.h` 里已经有这三处地址，原指令和 1.0.0 相同。

合并时的检查（M4 Mac）：`scripts/verify_v143_output.py` 加了渲染尺寸用例：不设时这四处不变；设 960x540 时正好改这四处，数据页 +16 是 960、540，Unicorn 跑补丁后的指令，存进 +0xcc4 / +0xcc8 的是 960、540，+0xcc0 的输出宽度仍是 1920；IPA 导出只在设了变量时编进补丁；`960x540x` 这种值直接报错（只放宽这一处解析，校验就失败）。shell 里留着的 `TOTK_RENDER_RES` 不会影响别的用例。iOS 的分支用 iOS SDK 编过（`-Werror`）。实机两局（存档副本，同一个神庙入口）：不设变量时场景渲染目标是 1600x896（1.4.3 自己的尺寸），设 `1280x720` 时是 1280x720，半分辨率的跟着变成 640x360，输出画布仍是 1920x1080；两局截图正常，红字一样（13 行，都是原有的），音频 0 欠载。

画布宽于 1920 时（PR #86，2026-10-20 合并）：游戏会把场景尺寸再乘上“输出宽度 ÷ 1920”，两个方向都乘（实测 2560×1440 画布上设 2560×1440 实际渲染 3408×1920，3440×1440 画布上 6160×2576），而且场景大于 1600×900 时 `DynamicTextureAllocatorMem` 不够，一两分钟后在分配器（`main+0x1c2d20` / `0x1c2f20`）里崩溃。现在数据页里写的是“要的尺寸 ÷ 画布倍数”，启动时和按 3 键换画布时（通知游戏之前）重新写，所以每种画布上渲染的都是要的尺寸。纹理堆、Graphics 和应用内存池按画布和场景各自的像素倍数一起放大，场景部分留 1.6 倍余量（这个余量是在除掉画布倍数之前量的，现在偏大，安全）。堆配置补丁是 `<画布>-scene-<场景>`（`make_output_res_overlay.py --scene`，只有 1.4.3），`build_app.py` 会生成 1920×1080 / 2560×1440 两种画布配 1920×1080 / 2560×1440 两种场景；别的组合启动时会停下，并打印生成它的命令。**画面变化**：画布宽于 1920 时，同一个 `TOTK_RENDER_RES` 比以前软，因为以前其实是按画布倍数超采样了；要更清楚就设更大的场景尺寸。合并时验证：2560×1440 画布 + 2560×1440 场景跑 3 分钟、中途两次按 3 键，没有崩溃，帧时间 p50 约 9 ms；`verify_v143_output.py` 和 `verify_v143_timing.py` 通过。

## 1.4.3 固定分辨率（TOTK_FIXED_RES）

游戏的动态分辨率控制器（`main+0x584300`，每帧由渲染器更新函数 `main+0x58196c` 调用）用 24 个帧时间样本预测下一帧的开销，在 100 % / 90 % / 80 % 几档之间切换场景分辨率（3024×1890 画布上实测场景在 3024×1888、2712×1696、2416×1512 之间变化）。控制器把当前档的缩放比例作为 float 放在 `x0` 低 32 位返回，调用方把 `cc4 * 缩放 / cc0` 存进渲染器 `+0xccc`。

所有分支都从同一个结尾离开，把缩放比例送进返回值的只有一条指令：`main+0x5848a8`，`mov w9, w23`。设置 `TOTK_FIXED_RES=1` 时把它换成 `mov w9, #0x3f800000`（1.0f）：控制器照常运行、照常选档，但每一档都是 100 %。`TOTK_RENDER_RES` 选的场景尺寸不变，只是不再动态缩小。原始指令在写入前核对，不匹配即 `runtime_fail("fixed resolution patch: main does not match 1.4.3")`；iPhone / iPad 的内嵌代码不能运行时改，只在 Mac 上提供。

验证（M5 Mac，1.4.3，3024×1890 画布、场景为画布尺寸）：不设时，进入洞穴后很快降到 2712×1696；设了之后场景一直是 3024×1888。只在一个场景（地下洞穴）和一个画布尺寸上验证过。
