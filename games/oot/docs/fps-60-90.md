# OOT：60–90 FPS 的实测与瓶颈

2026-11-07。目标尚未达到：同一活动存档的村庄静止约 29 FPS，转镜头约 32 FPS。保留原画质、分辨率及实时时步修复；不得以补帧计数、游戏慢动作、室内成绩或 GPU 时间倒数冒充达标。

## 对照条件

同一个桌面 App、同一活动 profile，Apple M4 / 16 GB。当前显示器 60 Hz；渲染 FPS 与屏幕实际显示的独立画面数分别验证。90 个可见独立画面需要足够刷新率，不能通过修改计数器实现。

主渲染附件实录 1536×864，部分目标 2048×1152。本轮各局窗口 drawable 均为 1815×1017（现有窗口状态），未降低设置。历史 57–58 FPS 在林克家室内，约 700–780 draws；本次村庄约 2900–3100 draws、139 passes，不是同场景回归证据。

## 已定位并修改的同步

`pool_demand_prepare` 需要在 CPU 上读取不可变描述符输入，以避免整池纹理实体化。原实现发现任意待执行写入后，结束当前编码段、提交并等其反馈完成。真实记录的 8 次等待中，输入均为 5,767,200 字节；相交的写入来自较早提交中的 raw store，全地址保守范围；当前编码段没有相交写入。

修正按每个输入的实际字节范围，取最后一个可能写入它的提交栅栏。较早提交中的 GPU 写入等待现有队列 GPU event；当前编码段中的写入仍走原来的切段并等待路径。raw store、范围溢出和未知生产者保持保守。

不能只改为 `mtl_wait(较早栅栏)`：受控反例表明 Metal 提交反馈可以晚于后续无关工作。GPU event 与 CPU 完成回调分开：本修正只等待被追踪的 GPU 缓冲写入，不提前推进 `g_done`，不提前执行 CPU post-op，也不提前回收资源。

Mac 默认开启；iOS 默认保持原路径。`OOT_POOL_WAIT_PRECISE=0` 或 `flag pool_wait_precise 0` 恢复旧等待，1 开启；`flag pool_wait_stats 1` 输出真实 prior/current 等待计数，`flag pool_wait_trace 1..16` 限量记录来源。

## 编译器与实际乘法成本

已用当前最热的实际 shader 比较安全数学下的 O1 / O2，以及实际 128 线程组与编译器默认上限。GPU 管线均创建成功，未出现上游提到的控制流回退或数量级代码膨胀；本次不能归因于该上游案例。

SPIRV-Cross 的扩展乘法辅助函数带有 optnone。默认关闭的诊断用 uint 重载内联 32 位无符号乘法，int 重载保持原辅助函数，安全数学不变；隔离正常预编译库和管线存档。独立 Metal 4 GPU 对边界及随机的无符号 / 有符号输入共 8,388,608 项精确比较通过，故意破坏高位的反例检出。重复乘法微基准约 0.842 → 0.571 ms，只说明原语成本，不代表游戏帧率。

同 App / 存档、二进制 638880c9b63af5ca02ead57c3ab2f9b443aa75a6725a8f5c8a2819a81599a53b，旧 / 新 / 旧三次独立启动：28.667 / 29.805 / 28.545 FPS。新路径 GPU CB 时间和约 31.14 ms，旧路径约 32.22 ms；CPU 约 15.5 ms。三轮均无现建管线 / 库及 GPU 错误，正常退出 0。截图未见明显新增错画，原有白雾仍在。新路径约提升 4.2%，尚不足以达标。

第一次候选冷预热因关闭整个管线存档索引而扩大了计划，脚本又只按帧号判定进度，120 秒自动关闭；该轮没有进世界，不算 FPS 或 GPU 失败。修正为保留索引、仅隔离候选键，并识别真实预热日志后，候选完成。正式修法应落在 typed OpUMulExtended 的 32 位标量生成分支，保留 SMul / 向量 / 64 位；当前源码替换仅作默认关闭的诊断，尚未作为正式优化交付。

## GPU 写入范围与写入边界

raw-writes1 的 6 个完成帧都执行同一真实计算 shader（5a2e37058f21c8a5…），网格 169×1×1。GPU 页集合每帧 11 页，均在客体地址高位 0xE，溢出 0；实际绑定的常量槽 1 为 384 字节不可变 arena 数据，已对应 frame / fence / shader 留存。等待描述符位于 0xD。该采样证明这些帧存在全地址失效误判，不能将页集合或地址前缀当作所有帧安全的省等规则。

新增默认关闭的写入边界候选：在 raw-store 派发之后提交该 GPU 段并发出独立队列完成事件；依赖者只在所有相交生产者都具有有效完成票据时等该事件。任何未知写入 / 待复制保留原完整等待。同一范围后续再次写入会清除旧票据。不推进逻辑 fence、CPU post-op 或 arena 回收。

独立真实 GPU 检查现为 67 项，覆盖同一逻辑提交中相关写入完成、后续无关工作仍阻塞，以及重复写入清票据；旧整段等待和故意漏等由反例检出。UBO 16409 项回归通过。真实游戏旧 / 新 / 旧 / 新对照进行中，探针通过不表示 FPS 达标。

## 写入域证明候选（实验，默认关闭）

离线工具使用同一固定翻译器产生的 typed SPIR-V，识别 PhysicalStorageBuffer 的所有写入，包含 store、atomic add 和 atomic max；不能只证明 5 处普通 store 就忽略原子写入。原型用 SSA、保守 unsigned32 区间、CFG 可达性与仅限非循环值的分支约束求解。初版每工作组分区覆盖 169 组、385 处可执行普通 store；增加上下文约束后能直接覆盖整个网格的 14 处 store / atomic 调用。

全部指针低 32 位按任意 uint32 处理，无须固定到捕获的地址。当前完整网格输出高位集合为 [0,5]、[14,19]、[29,31]，排除描述符所在高位 13。24 个常量字、精确网格 / local size、实际 SIMD 宽度 32 是专门化条件。该结论只适用于输入条件吻合时，且 raw helper 的 guest low/high 参数 ABI 目前仍为人工核对；不能称为完整自动化的正式编译器证明。

新增默认关闭的 raw_write_domain 消费器：源码及反射文件 SHA-256、翻译链、shader key 全部匹配才加载外部证明；每次消费只读取本次实际绑定的不可变 arena 常量，并逐字核对条件。live 输入、缺失 / 变化的字、间接派发、网格 / 线程组 / SIMD 不符全部退回全地址失效。没有按游戏地址前缀或采样页集合直接省等，也不提前推进 fence / CPU post-op / arena 生命周期。

- `pool_input_ids`：同一张表（地址、大小、池容量、池内存代号、宿主写回代号相同）保留“可能用到的贴图号”并集；新抓取只扫自上次扫描以来被写过的页（脏页写代号，新函数 `nvn_dirty_runs_since`）。并集只多不少（最坏等同整表路径）；宿主写回不标脏页，代号一变就整表重扫。每帧扫描从约 360 万字降到约 4 千字。`OOT_POOL_IDS_INCREMENTAL=0` 回到整表扫描。探针 `probe-gpu-memory-demand` 增加 6 项（首抓整表、改一页只扫一页、新旧号都在、未变不重扫、宿主写回整表重扫），关掉增量时该项按预期失败。
- 主命令分配器上限 8 → 64：队列排序把每次挂起 / 恢复分开提交（每帧约 18 个命令缓冲），8 个时回放每帧约 2 次等 GPU 腾出分配器；现在 0 次。
- 恢复挂起项时 uniform 快照只遍历还没执行的部分（游标各层的下一条 + 未开始的句柄）。
- 队列排序拆成两把锁（队列结构 `g_qo_mu` / 编码回放），并实现 `OOT_QO_ASYNC=1`（默认关）：flush / CPU 信号只唤醒队列排序线程，出图排在本帧后面由它执行，取图等这张图上一次出图执行完；配套的生命周期规则（宿主命令副本、贴图 Finalize 都推迟到更早提交回放完）在开着时必需。实测 38.0 fps，不如原地回放的 39.5：游戏每帧都等上一帧 GPU 完成，链条没有变短。保留作对照。
- 命令缓冲内录的 `FenceSync` 在提交入队时即登记为待定（按队列序号结算），不再在回放完成时由旧条目覆盖同一同步对象的新状态。
- 默认关的诊断：`OOT_QO_RING_AT`（事件环）、`OOT_QO_CHECK`（回放前校验命令流）、`[queue-order]` 行新增最长挂起时长与“信号后停下”计数、`[descriptor-ids]` 行。

**结果**（默认设置一局）：39.7 fps，整帧 25.2 ms，回放 CPU 14.6 ms，GPU 21.7 ms；整屏白帧（>1024/16384 高亮点或平均 > 200）0；截图正常。之前用“bright>0”统计的“亮帧”只是几十个高光像素，不是白帧。

**下一步**：现在 GPU 21.7 ms 是最长的一段，但整帧 25.2 ms 仍大于它——链条上 GPU 在等“CPU 信号后的回放”。缩短信号后回放（回放 CPU 其余热点：`prepare_draw_textures`、`draw_inner`）和 GPU 本身（植被片元、同目标通道拆分）两条都要做。

## 2026-11-08 下午（Claude）：网格阶段暂存区搬到显存，44.3 → 47.9 fps

**定位**（同 App、同活动存档、村庄静止，`flag skip_ms` 逐个跳过网格着色器）：GPU 22.2 ms 里，网格着色器 fed302d7 占 3.5 ms、eb021183 1.6、604134a5 1.0、bc9d26e2 0.4。对 fed302d7 做单变量替换（手改缓存里的 MSL、同一局实测）：主体不执行 −3.2 ms；原始读取全部换成空实现 −3.0；只翻译地址不读 −1.5；关掉现有单条目地址缓存 +2.3；再加 16 KB 线程组内存 +3.6。即它的时间全在“地址翻译 + 读取”的**延迟**上，而且对线程组内存量极其敏感——这个阶段的暂存区（128 顶点 × 约 25 分量 = 11–16 KB）本身就把每核能同时驻留的线程组压到两三组（Instruments 11-06 测到该阶段占用率 4.7%），延迟盖不住。

**根治**（翻译器 `MeshStage.cs` + 宿主 `nvn_mesh_tasks.inc`，链 `oot-native-v18-mesh-device-stage`）：阶段暂存区超过 4 KB 的网格着色器改用宿主绑定在 mesh buffer 28 的显存缓冲：头部 word 0 计数器、1 槽位掩码、2 槽位步长（4096 字）；word 4 起每槽一个占用标志；word 8192 起是槽位（Mac 4096 槽 = 64 MiB，iPhone 1024 槽 = 16 MiB，`OOT_MESH_SCRATCH_SLOTS` 可改）。线程组开头由 0 号线程取槽（计数器 +1 取模，再对该槽标志做 exchange，占用则继续找），输出写完后释放；槽位在线程组运行期间绝不会被复用，与 GPU 调度顺序无关（只按计数器取模不行：16 槽 / 20000 组的探针负对照测到 220 万个字被别的活线程组覆盖）。主体里的 `threadgroup` 引用、原子字节写和屏障相应换到 device 地址空间；若主体还有别的 threadgroup 用法就保持原样。任务（object）阶段不变。空导出变体（`OOT_MESH_EMPTY_EXPORT`，默认关）提前返回前先释放槽位。

**验证**：`probe-gpu-mesh` 7408 项（新增 20000 组争 16 槽三轮：无重叠、全部释放；负对照必失败）、mesh-batch 39、draw-barriers 24672、memory-demand 367、ubo-snapshot 16409、stor-alias 25、17 个单元测试。默认设置实测（新链冷缓存一局）：**47.9 fps**，整帧 20.8 ms，GPU 20.5 ms（修前 22.2），白帧 0，截图正常（手改实验里同着色器连续绘制共用槽位时草地全是白色亮点，正式实现没有）。最贵通道 #37 从 3.55 ms 降到 2.28 ms。

**代价**：每组多写/读一遍暂存区到显存（大多命中 L2），64 MiB 常驻缓冲；首次启动因换链全部重新翻译。

**否决的方向**：地址缓存做成 2 / 4 条目（LRU 或 FIFO）——GPU 后端编译时间从 2.8 s 涨到 20 s / 超过 75 s（60 多个内联调用点各带一串比较），c4a/c4b 两局就是卡在 `newRenderPipelineStateWithMeshDescriptor` 里不返回（`measure.py` 现在检测到帧号 30 s 不动会自动 `sample` 并 `flag qo_dump` 打印队列事件环）。离线复现：`tools/psotime`（同游戏一样的编译选项和网格管线描述）。

**下一步**：剩余 GPU 20.5 ms 里，网格阶段仍是大头之一（翻译 1.5 ms + 读取 1.5 ms 只算 fed302d7）；现在占用率上去了，再看每个线程组里原始读取的翻译次数（82 次/线程，基址只有 5 个常量缓冲字）——按基址静态分配缓存槽位（翻译器侧，不增加每个调用点的比较）是下一个候选；其后是 683×384 的全屏材质通道（片元 2.2 + 2.0 ms）和计算 9e6b00b0（1.4 ms）。

### 同日稍后：阶段内存字节写改直写，47.9 → 49.4 fps（链 v19）

每个网格着色器都有一个把 8 位写进阶段内存的辅助函数（三角形索引字节、图元数），翻译器只能用 compare-exchange 循环往 uint 数组里插 8 位。Metal 的 `uchar` 写在 threadgroup / device 内存上都是按字节的（相邻字节由别的线程写互不干扰），包装器（`MeshStage.Wrap`）把这类辅助函数识别出来（`insert_bits(..., 8u)` + CAS + `>> 2` / `& 3` / `<< 3`）换成一条字节写，小端字节序不变。手改 fed302d7 单测 GPU 20.5 → 19.7；全部 43 个阶段着色器改后默认设置实测 **49.4 / 48.7 fps**，GPU 19.9 ms，白帧 0。

顺带：槽位获取加自旋上限（65536 次后带着当前槽继续并记入头部 word 3，日志红线），每 600 帧打印“此刻被占槽位 / 计数器 / 强取次数”（两局均为 0 / 0）；请求可带 `stage_device=false`（`mesh_index_bounds_gpu.py` 用，它的 compute 包装只能读 threadgroup 阶段内存）。验证：probe-gpu-mesh 7408、mesh-batch 39、draw-barriers 24672、memory-demand 367、stage_payload_gpu 28、mesh_index_bounds_gpu 34、17 个单元测试。

一次 GPU 挂起（bs2）：进世界时 GPU 停止完成，16 个命令缓冲全是 `InnocentVictim`、没有肇事者，同一时刻我在并行跑 GPU 测试工具；同包再跑两局正常。以后游戏局期间不并行跑任何 GPU 工作。

### 同日傍晚（Claude）：gRPC 定时器线程空转一整核——根因与根治（ck1–ck5）

**现象**：tp1 里一个游戏线程每帧 18 ms 在 P 核上只做 clock_gettime 进运行时（见上节）。诊断 TOTK_CLOCK_POLL_LOG 改为记两级客体返回地址后（ck1）：线程 0x29a3c4 每秒 603 万次时钟调用，来自 main+0x21e479c（`grpc_core::ExecCtx::Now()`，调用者 main+0x21f80e0 = `grpc_timer_check`：读 TLS[0x28] 的 ExecCtx、与 TLS[0x50] 的 g_last_seen_min_timer 比较）和 main+0x21e4e58 / 0x21e4f1c（`gpr_convert_clock_type`，调用者 main+0x21e70a4 = `gpr_cv_wait`）。GOT 槽按 .dynamic 解析：0x4cc0c88 = nanosleep、0x4cc0c48 = `_ZTHN9grpc_core7ExecCtx9exec_ctx_E`——游戏里嵌着 gRPC。

**链路（全部反汇编核对）**：`gpr_cv_wait`（main+0x21e7050）→ 换成 REALTIME 绝对时刻 → SDK 的 `pthread_cond_timedwait`（sdk+0x171990）→ 用 **SDK 自己的** `clock_gettime`（`bl sdk+0xb28f0` → sdk+0xb52a0，不是 main 导入、被我们覆盖的那个）算相对超时 → sdk+0xb52a0 经槽 sdk+0xeb0018 跳到 `nn::time::GetStandardUserSystemClockCurrentTimespec`（sdk+0x5d8bb0）→ 它先查 `nn::time::detail::SharedMemoryClient` 的初始化标志 `[client+0x48]`，为 0 就返回 0x74 → SDK clock_gettime 置 errno=11 返回 -1 → pthread_cond_timedwait 把 errno 当返回值（sdk+0x171ad0），**根本没走到 nn::os TimedWait / svc 0x1C**（ck2/ck3 的 TOTK_CONDWAIT_LOG 里该线程没有任何等待记录）→ `gpr_cv_wait` 接受 11（`cmp w0,#0xb`）当正常唤醒 → `timer_main_loop` 空转。ck3 实测读出：`sdk time SharedMemoryClient sdk+0xf7e8e8 initialized=0`，`REALTIME -> sdk+0x5d8bb0, MONOTONIC -> sdk+0x5d8770`。

**根因**：我们用 HLE 替换了 `nn::time::Initialize`（SDK 的时间共享内存客户端因此从不初始化），又单独把 main 导入的 `clock_gettime` 覆盖成宿主时钟——进程里同一个 clock_gettime 有两份实现，SDK 内部那份是坏的，只对直接调用 main 导入的代码“看起来正常”。TOTK 的 time_host.c 没有这条覆盖，它是 2fc450da 初始提交带进来的。

**根治（`time_host.c`）**：实现 SDK libc 时钟提供者 `nn::time::GetStandardUserSystemClockCurrentTimespec` / `GetAdjustableUserSystemClockCurrentTimespec`（宿主 CLOCK_REALTIME，纳秒）和 `GetStandardSteadyClockCurrentTimespec`（宿主连续时间，和 steady_seconds 同源）；去掉 main 的 clock_gettime 单独覆盖——全进程只剩 SDK 的 clock_gettime 一条路，源头都是宿主时钟。提供者是 SDK 启动时从按名 JUMP_SLOT（sdk+0xe89df8 / e00 / e08）装进槽的，所以按名覆盖就够。**撤回的两项**：loader.c 让相对重定位也尊重覆盖（槽的文件值是滴答时钟默认 sdk+0xaf0a0，不是 nn::time 函数；离线核对三模块 553,354 条相对重定位无一指向被覆盖函数，日志 redirected=0，无作用）；memo 跨提交命中（命中数/证明数 dp1 9.0% → ck3 7.3% / ck4 8.0%，没有提高，恢复原条件和探针期望）。

**验证**：ck4（修后 + 诊断）：`[totk-clock]` 每秒 5,308 次（ck3 为 1,810 万），榜上只剩 SDK 的正常轮询（sdk+0x7d432c ≤1,615/s），gRPC 线程不再出现。ck5（最终构建，默认设置，含同事的 1536×864 固定分辨率 6d8965d8）：**44.62 fps**，整帧 22.4 ms，GPU 24.0 ms，回放 sub_cpu 11.78 ms，白帧 0，截图正常；`ps -M` 两次快照 12 s 内各线程 CPU：最高 57.5%（游戏主线程含内联回放）、31.9%、9.1%，其余 ≤7%——没有接近 100% 的线程（修前一个游戏线程 ≈ 一整个 P 核）。fps 不变是因为 1536×864 下 GPU 24 ms 封顶；省下的是一整核 CPU 与功耗。六个 GPU 探针通过，仓库 1526 个单元测试通过（7 跳过）。

### 同日晚（Claude）：1536×864 下 GPU 在干什么（ct2：默认设置 + DM_NVN_ENC_LABEL=1，xctrace 4 秒 Performance Limiters + Shader Timeline）

**时间线**（`tools/ct_shaders.py` 的 encoders.tsv，113 帧）：整帧 24.33 ms，GPU 编码器区间并集 **21.78 ms/帧，空闲间隙 2.55 ms/帧**（每帧 222 个间隙，绝大多数是编码器之间几微秒的调度缝；235 个编码器/帧 = 106 个渲染通道 × 2 通道 + 约 27 个计算 + 拷贝）。**帧首约 2 ms 没有游戏工作**：预提交的帧首计算（5a2e3705，0.8 ms，核占用 16%）之后是 0.41 ms 间隙 → 一个 0.98 ms 的无标签计算编码器（GPU 保活自旋核，只在没有游戏命令缓冲在飞时启动）→ 0.57 ms 间隙 → 2.99 ms 处才开始真正的渲染。对照 qa12 的 CPU 帧链：游戏主线程每帧在 SyncWait 里等 GPU 约 8 ms，醒来后 0.5 ms 内提交下一块工作（回放 0.33 ms）——帧首空闲 = 栅栏唤醒 → 游戏代码 → 我们的内联回放 → 提交 → GPU 启动这一串的延迟。要缩短它只能让这段 CPU 更短（回放更快）或让游戏提前多排一帧（它自己的栅栏逻辑决定了只领先一帧）。

**计数器（各组占峰值的百分比，`tools/ct_counters.py`）**：
- 1536×864 渲染通道的片元：FS 占用 44.7%，指令吞吐限制 46%，片元发射限制 71%，F32 36%，整数/条件 27%，贴图读缓存 29%，L1 逐出率 57%，栈读写带宽高（寄存器溢出）。最大的物件通道 e0eb0a01（704 绘制）：占用 28.7% 而占用管理器目标只有 30%——**寄存器压力限制了并发**；指令吞吐 68%、发射限制 96%、F32 54%、栈读写 194/187。全屏通道 bc214ce5：寄存器 / 栈读写 770/884 与 394/388——大量溢出。
- 网格（顶点通道）：占用 4.3%（目标 88–99%），发射受限于输出分配（已知，见上文微基准）。
- 计算：核占用 25%，计算发射限制 70%，F16 限制 61%（上采样网络）；9e6b00b0 发射限制 86%、占用 26%；5a2e3705 占用 16%；**aba48e1a 占用 0.75%、指令 0.3%，却每帧占 0.9 ms——它在等（紧跟一个拷贝、新 fence 的第一个编码器），待查它等的是什么**。
- **FP16 不是可用的杠杆**：这些片元 SPIR-V 里没有 16 位浮点类型（e0eb0a01：FMul 517、FAdd 212、Fma 410，UnpackHalf2x16 只有 12 个、PackHalf2x16 0），游戏原始着色器就是 FP32；翻译器（vendored Ryujinx 1.3.2）把 Ampere 的半精度成对指令按 F32 算，也不涉及这些通道。
- **pass_gpu 的小通道数字不可信**：passes.tsv 里 84bd08d0 的 120×67 / 240×135 通道每帧有一个 1.4 ms（同一 fence 内、与前一通道无间隙），Instruments 的同名编码器区间只有 0.03 ms；pass_gpu 的结束时间戳包含了等待 / 延后，按通道排 GPU 时间要以 Instruments 为准。

**同目标连续通道**（qa12 一帧）：17 组 44 个通道、合计 4.5 ms，其中大多是 2–4 个只有 1–2 次绘制的小通道（mip 链、384×216 分层），能合并的收益小；真正贵的是 1536×864 的 20 个多绘制通道（9.2 ms）和 19 个 ≤2 绘制的全屏通道（2.8 ms）。

## 2026-11-08 晚（Claude）：uniform 快照改用录制时预排序的范围表；句柄池捕获增量化（656bcb5f）

## 2026-11-09 凌晨：CPU/GPU 帧重叠安全化（TOTK_SYNC_LAG=2 的白帧根因与修法）

背景：默认 App 1536×864 固定 + MetalFX ≈ 49–50 fps（pz6：frame 19.9 ms，CPU work 10.7 ms，其中回放 10.1 ms）。放宽帧首栅栏等待（TOTK_SYNC_LAG=2，sl2）61.2 fps / 15.7 ms，但 2700 帧里 600 帧全白。本节用数据回答“谁在 GPU 还没读完时改写了什么”，并给出不猜缓冲用途的根本修法。

**清单（lr1：TOTK_SYNC_LAG=2 + OOT_RACE_CHECK=1，诊断本身很重，19 fps，只看种类不看时间）。** OOT_RACE_CHECK 现在覆盖全部 GPU 直读客体内存的种类：'u' 实时 uniform、's' 只读存储、'w' 可写存储、'i' 索引、'v' 顶点、't' 贴图上传源、'c' 拷贝源、'a' 间接派发参数、'm' 网格计数源；每条竞争带写入者 pc（脏页记录环加了时间戳，`nvn_dirty_recent_snapshot`）。F600→F1200 的增量：'s' 52409 / 登记 127891，'w' 2914 / 42315，'m' 2630 / 12895；'u' 新增 0，'v' 0 / 288357，'i' 0 / 342603，'t' 0 / 1134，'c' 新增 0，'a' 0 / 3983。**结论：游戏中被 CPU 提前改写的 GPU 输入只有存储缓冲（含可写的）和网格计数源；顶点、索引、贴图、拷贝源不冲突。**

**根本修法：每页 GPU 读栅栏（OOT_GPU_READ_FENCE=1，`nvn_dirty_read_mark` / `rd_check`，nvn_dirty.c）。** 提交编码时，GPU 直读的每条客体范围按页记下该提交的栅栏号并设只读；CPU 写到这样的页就在缺页处理里等到该提交完成（`g_done`），而不是在帧首等整帧。编码线程（它要提交这条栅栏）和 Metal 完成回调线程（它们替 GPU 写信号量 / 计数器结果，`g_done` 在其后才更新）按线程私有标志豁免；销池路径（持 g_slot_mu）不等待。rdf1 没有这条豁免：完成回调写 `*ops[i].val` 时撞上只读页，每次等到 3 s 超时，累计触发 GPU 看门狗（“16 个命令缓冲 10 秒无完成”）而中止——这是第一次实测就学到的。

**rdf2 / rdf3（TOTK_SYNC_LAG=2 + OOT_GPU_READ_FENCE=1）：白帧 0**（1262 / 1242 帧里 bright≥1000 的 0 帧；sl2 的白帧 bright≈4800、avg 233），即读栅栏覆盖是完整的。但 fps 42.6 / 41.7（frame 23.3 ms）：每帧约 8 次写等待、合计 22 ms（各线程之和）；每帧标记约 5000 条范围 / 12.5 万页，缺页 150 次，mprotect 0.37 ms。等待把重叠吃光还多了开销。

**等待归因（rdf3，`tools/rd_waits.py`，日志 `[rd-wait]` + `[rd-frame]`）。** 每帧 25 条提交；800 次等待里 's' 1246 ms、'w' 883 ms、'm' 224 ms。按提交位置：倒数第 3 条提交（主场景：passdump 里 35 个通道、1972 次绘制、网格批）占 870 ms（'s'）+ 224 ms（'m'）+ 110 ms（'w'）；倒数第 4 条（7 通道 506 绘制）264 ms（'w'）；倒数第 8 条（61 次派发的计算提交）300 ms（'w'）。每帧第一次等待等的就是倒数第 3–4 条——**CPU 在帧首写的，正是上一帧快结束时才读的缓冲**，所以“写时等待”本身几乎等于帧首等整帧。

**写的是什么（把等待页映射到 passdump 的 B 记录）。** CPU 每帧只改各缓冲的一两页：0xddfde6040（98 KB 只读，页 0，writer main+0x347b04，305 ms）、0xdfeecd000（720 KB 只读，页 0，302 ms）、0xcdb76e900（40 KB 只读，2 页，240 ms）、0xdde8cd000（23 KB 可写，1 页，216 ms）、0xddfb31000 / 0xddfb2b000（4 KB 可写，各 1 页，114 / 107 ms）、0xcdb75b700（48 KB，4 页）、0xce0421c00（18 KB 只读）、0xce043a400（192 KB 可写，6 页）、0xddfb37000（8 KB 可写）。主场景片元着色器绑定的 9.5 MB 存储缓冲 0xddea36000 没有任何等待：CPU 不每帧写它。即被改写的数据总量很小（约 20 页）。

**第二步（rdf4）：只读的小范围按编码时刻快照，网格计数源由 CPU 在编码时读。** 只读存储缓冲走现成的 `sbuf_snap_get`（OOT_SBUF_SNAPSHOT=<KB 上限>，去重改为“同一提交内、拷贝后没有 pend 条目落在该范围”），快照过的不再做读栅栏标记；网格批 8 字节 {count, first} 源与网格间接 4 字节 count 在没有待完成 GPU 写时直接读内存填入（OOT_MESH_SRC_CPU，随 OOT_GPU_READ_FENCE 默认开）。游戏在主机上让 GPU 读到的就是提交时刻的值（栅栏之前它不改这些缓冲），所以编码时快照与执行时直读等价。可写（'w'）缓冲这次仍走写时等待：GPU 可能写它们，提交时拷贝会丢 GPU 结果，要先量 GPU 是否真写、CPU 是否读 GPU 结果。

**rdf4（+OOT_SBUF_SNAPSHOT=1024，网格源 CPU 读）：白帧 0；'s' 等待 1246 → 149 ms，'m' 224 → 0；剩余等待几乎全是 'w'（2224 ms / 191 帧，每帧约 12 ms 各线程之和）；fps 45.2，帧时间双峰（p10 6.7 / p90 37.5 ms）。** 快照每帧拷贝约 21.8 MB（同一范围在多条提交里各拷一次；按脏页复用能降到 1–2 MB），回放 CPU 12.3 ms。把剩余等待的页映射到绑定（passdump B 记录）：192 B 参数块 0x45a487f00（主场景 279 个只读绑定；同页 0x45a487fc0 的 64 B 由主场景计算核 6bc69116 可写绑定；writer main+0x337608 / main+0x651a44；986 ms）、23 KB 计算核暂存 0x45e8cd000（主场景与倒数第 7 条的计算核可写；423 ms）、4 KB ×2（倒数第 5 条的计算核）、48 KB / 192 KB / 16 KB ×2 / 32 KB ×3（倒数第 9 / 13 条的计算核）、64 B 计数器（424b9852）。即：**游戏在帧首先写这几页参数 / 计数器，它们又被上一帧主场景里的计算核可写绑定，于是整段 CPU 帧都排在上一帧主场景之后**（rdf4 的 23 ms = 12.4 ms GPU + 10 ms CPU + 开销），与基线的串行等价，还多了开销。

**基线时间线（tlb1，TOTK_TIMELINE 40 帧，`tools/tl_frames.py`）：每帧 26 条提交，GPU 忙碌并集 16.9 ms，帧内空闲 2.4 ms，帧边界空隙 0.1 ms，游戏帧首栅栏等待 2.7 ms。倒数第 2 条提交（主场景直到后处理，一个命令缓冲）GPU 12.4 ms，其余各条 ≤1.5 ms，出图后只剩 0.2 ms。** 所以“只放宽到最后一条读实时输入的提交”没有可重叠的尾巴；重叠的唯一空间是下一帧前半段（约 5 ms CPU：帧首逻辑 + 早期小提交的编码）盖住本帧主场景的 12.4 ms GPU，这要求帧首写的那几页参数 / 计数器不等主场景——它们的 GPU 结果是否被 CPU 读、读哪些字节、CPU 又写哪些字节，是下一步必须先量的（OOT_NOREAD_PROBE：出图后把本帧可写绑定的页设 PROT_NONE，记录第一次 CPU 读 / 写的地址与 pc）。另一条路是让 CPU 更早把主场景提交出去（早期阶段的编码时间每省 1 ms 整帧就少 1 ms），与重叠互不排斥。

### 2026-11-09 10:00 校正：720p 的“帧时间双峰”是测量口径问题；显示器是 100 Hz
